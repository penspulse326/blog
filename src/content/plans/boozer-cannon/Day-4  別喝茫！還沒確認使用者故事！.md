## 持續迭代

起始的 prompt 描述的功能範圍只有這樣：

```
1. 使用者可以新增酒譜
2. 酒譜中的每種材料可以再標示材料的品牌
3. 新增酒譜可以上傳照片
4. 使用者可以收藏酒譜或按讚酒譜
```

讓 AI 根據目前迭代的成果產出使用者故事：

```
**酒譜建立與管理**

* 作為創作者，我想要自由填寫酒譜名稱、基酒、調製技法，以便記錄並公開我的原創或經典配方。
* 作為創作者，我想要在每種材料旁標註推薦品牌與自訂 ABV，以便精準還原特定風味。
* 作為創作者，我想要上傳酒款成品照片，以便讓酒譜在列表與詳情中更具吸引力。
* 作為創作者，我想要透過多選晶片為酒譜標記多種風味標籤（如酸爽、煙燻、氣泡感），以便標註口感輪廓。
* 作為創作者，我想要在輸入杯型、冰塊與裝飾物時享有「常見選項快選 + 自由文字輸入」，以便兼顧輸入效率與創意自由度。

**風味與探索搜尋**

* 作為調酒愛好者，我想要依照風味輪廓標籤（如花香、草本、甘甜）一鍵篩選酒譜，以便依照當下心情挑選想喝的酒款。
* 作為調酒愛好者，我想要使用中英文或常見別名（如「坦奎利」或「Tanqueray」）進行搜尋，以便精準找到對應品牌或杯型的酒譜。
* 作為調酒愛好者，我想要依照酒精強度級距或濃度高低排序酒譜，以便挑選適合聚會或獨飲的飲品。

**酒精濃度與調製分析**

* 作為調酒探索者，我想要系統自動預估調酒的最終出杯 ABV，以便在免手動計算的情況下掌握醉度。
* 作為調酒探索者，我想要查看材料容量、融水量與純酒精的結構比例條，以便理解搖盪或攪拌等技法對酒體的稀釋影響。

**社群與個人化**

* 作為調酒愛好者，我想要為喜愛的酒譜按讚，以便給予配方作者肯定。
* 作為調酒愛好者，我想要一鍵收藏特定酒譜並快速切換檢視收藏清單，以便隨時查閱自己常喝的清單。
```

以 MVP 來說已經有收斂到我想要的範圍！

不過這個回復一開始其實長到靠北，不太像平常在讀的使用者故事。

但是幾乎用哪家模型都會有這個問題，數大便是美，總是瘋狂堆一些沒人想看的規格......所以需要再把除掉贅述才能變成易讀的文字，也可以考慮增加一些**全域規則，讓文字一開始就更精簡**，自己才比較好校稿。

## 再次拷問

不論是以前還是導入 AI 之後，對於每一次迭代，無論成果是好是壞，都要時刻檢視目前的方向，**保持思考才是把關 AI 交付品質的第一步**。

現在有個方向是我想重新確認的：

> 這個網站需不需要做 i18n？

因為調酒的原始資料大部分都是英文，我們隨便到一間酒吧說：

「我要內格羅尼！」

不論說出來的中文翻譯是什麼，調酒師也應該能快速理解大概是在指 Negroni 這杯酒。

這樣表單目前的呈現也怪怪，強制必填中文名稱，我的想像是中英文選一個必填就好，UI 就優先顯示有填的那個。

AI 懶人包：

```
### 1. 酒譜名稱欄位：擇一必填

強制填寫中文名稱在實務上會造成極大的摩擦力：在酒吧通常直接用英文點單，硬翻成「飛行」、「紙飛機」、「盤尼西林」、「左岸大道」，反而顯得突兀或讓使用者難以搜尋。

* 本地特調的痛點：如「木柵鐵觀音伏特加特調」、「島嶼記憶」，創作者當下根本沒有構思英文品名。

* 欄位設計：保留 `英文名稱 (Name EN)` 與 `中文名稱 (Name ZH)` 兩個獨立輸入框。
* 校驗邏輯（Validation）：「二擇一必填」。只要填寫任一欄位即可發布，另一個欄位留空為選填。

---

### 2. 為什麼這個產品高度需要 i18n？

* 若強制全繁中或全英文，會割裂使用體驗。
* 系統做好 i18n，背後的基酒分類（`gin`）、風味（`sour`）、技法（`shake`）都是語言無關的代碼（Code）。
* 台灣使用者搜「酸爽」，系統撈出包含 `flavor_sour` 的配方；外國使用者切換為英文搜「Sour」，看到的也是同一批資料。
```

雖然概念發散到 i18n 了，但對我來說設計方向也更完整一點！

## 小結

1. AI 產一堆 code 可以不看，但產品概念和輸出文案還是得親自確認一下才不會偏掉，**如果連自己都懶得讀，那麼方向可能已經開始有偏差**
2. 驗證操作流程時多少會發現不如預期的地方，我在每次修改中發現表單的一些問題需要釐清，持續迭代就好，**不需要追求一次產出就完美交付**
